# AGENTS.md - Developer instructions for the ansible-sshd role

## For end users

If you just want to use this role in a playbook, not change its code, *this file isn't for you.*
See [README.md](README.md) for role variables, usage examples, and supported platforms.
See [GitHub Issues](https://github.com/willshersystems/ansible-sshd/issues) if you want to report a bug or request a feature without writing code yourself.

## For developers

Follow these conventions when you change this role.
See [contributing.md](contributing.md) and [contribute.html](https://linux-system-roles.github.io/contribute.html) for the full contributor guide.

### How this role differs from the other Linux System Roles

This role comes from <https://github.com/willshersystems/ansible-sshd>.
It follows most Linux System Roles (LSR) conventions, but it is not generated from the central `linux-system-roles/.github` repository.
Do not copy rules from other LSR roles without checking them against this list.

- The role directory and the name used in tests is `ansible-sshd`.
  The collection name is `willshersystems.sshd` (`galaxy_info.namespace` and `role_name` in `meta/main.yml`).
  There is no `fedora.linux_system_roles.sshd`.
- The variable prefix is `sshd_` (internal variables: `__sshd_`), not `ansible-sshd_`.
- The role fingerprint string is `willshersystems:ansible-sshd`, not `system_role:sshd`.
- The role supports many more platforms than other LSR roles: EL 6-10, Fedora, Debian, Ubuntu, Alpine, FreeBSD, OpenBSD, NetBSD, AIX, OpenWrt, SUSE, and others.
  Do not assume systemd, RPM, or a recent OpenSSH version.
  Put OS-specific values in `vars/<Distribution>[_<MajorVersion>].yml`, not in task logic.
- The role keeps compatibility with old Ansible versions where practical (`meta/main.yml` has `min_ansible_version: "2.9"`, `meta/runtime.yml` has `requires_ansible: ">=2.15.0"`).
  Check existing code and comments before you use newer syntax (for example, `handlers/main.yml` avoids `systemd_service` on purpose).
- CI uses `ANSIBLE_INJECT_FACT_VARS=false`.
  Always read facts as `ansible_facts['name']`, never as top-level `ansible_name` variables.
- This file is maintained by hand in this repository.
  It is not overwritten by a central automation.

### Generated files - do NOT edit by hand

- `templates/sshd_config.j2` and `templates/sshd_config_snippet.j2` are generated by `meta/make_option_lists` from the fragments in `meta/`:
  `01_ansible_head.j2`, `10_top.j2`, `20_middle.j2`, `30_bottom.j2`, `options_body`, and `options_match`.
- The block between `# BEGIN GENERATED __sshd_option_vars` and `# END GENERATED __sshd_option_vars` in `vars/main.yml` is generated from `meta/options_body`.
- To add, remove, or change how an sshd option is rendered, edit `meta/options_body` and/or `meta/options_match` (or the `.j2` fragments), then regenerate:

  ```bash
  python3 meta/make_option_lists
  ```

- Commit the regenerated files together with the source change.
- Before you commit, verify with:

  ```bash
  python3 meta/make_option_lists --check
  ```

  This is also the `check_generated_templates` CI job.
  Besides checking the generated files, it fails when:
  - an option in `meta/options_body` has no `sshd_<OptionName>` entry in `meta/argument_specs.yml`, or `argument_specs.yml` has an `sshd_<OptionName>` entry that is not in `options_body`.
  - a variable validated in `tasks/assert_role_vars.yml` is not assigned in `tests/tests_invalid_input.yml`.
- `CHANGELOG.md` and `.README.html` are produced by the release process (see [contributing.md](contributing.md)).
  Do not edit them in a feature PR.
- `.ostree/packages-*.txt` is generated from `vars/*.yml` by `meta/make_ostree_packages_files`.
  Regenerate it when you change `__sshd_packages` in a Red Hat family vars file.

### Commit messages, PR titles, and PR descriptions

**PR title** MUST follow Conventional Commits format.
CI runs `commitlint` on the PR title with `.commitlintrc.js`:

- Format: `<required type><optional (scope)><optional !>: <required description>`
- Valid types: `build`, `chore`, `ci`, `docs`, `feat`, `fix`, `perf`, `refactor`, `revert`, `style`, `test`, `tests`.
- The type must be lower case.
- The description must not be empty, must not end with `.`, and must not be in start-case, PascalCase, or UPPER CASE.
- The header must be at most 100 characters.
- Commit body and footer lines must be at most 100 characters.
- Examples:
  - `feat: Add support for the PerSourcePenalties option`
  - `fix: Do not restart sshd when only a Match block changed`
  - `fix!: Remove deprecated variable (breaking change)`
  - `chore(formatting): Fix indentation in tasks/install.yml`
  - `tests: Cover invalid sshd_config_namespace values`

**PR description** MUST follow the template in `.github/pull_request_template.md`:

- "Enhancement:" (or "Feature:") describing what changed
- "Reason:" explaining why the change was needed
- "Result:" describing the outcome or impact
- Optional "Issue Tracker Tickets (Jira or BZ if any):"
- Optional "Assisted-by:" with the AI coding assistant and models used (see below)

Example:

```text
Feature: Add the sshd_manage_foo variable

Reason: Users cannot disable the management of foo.

Result: Users can set sshd_manage_foo: false to skip foo.

Issue Tracker Tickets (Jira or BZ if any): RHEL-12345

Assisted-by: Fish 4.3 using model Swim 6.2
```

For bug fixes, you can use "Cause:", "Consequences:", "Fix:", and "Result:" sections instead of "Enhancement:", "Reason:", and "Result:".
For other change types (`docs`, `refactor`, and similar), the PR or commit body does not need a fixed template, but it must still be descriptive.

This repository does not require `Signed-off-by:` in its PR template, unlike most other LSR roles.
If you use `git commit -s` anyway, that is fine.

### AI agent attribution

If the code you add was substantially generated by AI, mark it:

- Add an in-line comment next to the generated code, or at the top of the file after the SPDX line (if any):

  ```text
  # Assisted by <name of agent> using model(s) <name and version of model>[, <name and version of another model>]
  ```

- Add the same attribution in the git commit message and PR body:

  ```text
  Assisted-by: <name of agent> using model(s) <name and version of model>[, <name and version of another model>]
  ```

### Ansible tasks - `tasks/**/*.yml`

**General:**

- Use FQCNs for all modules (`ansible.builtin.*`).
  `ansible-lint` runs in CI with the config in `.ansible-lint`.
- `tasks/main.yml` validates input with `tasks/assert_role_vars.yml`, then runs `tasks/sshd.yml` only when `sshd_enable` is true.
  Keep any new work behind `sshd_enable`.
- SPDX headers are not used consistently: only `tasks/assert_role_vars.yml`, `meta/argument_specs.yml`, `tests/tests_invalid_input.yml`, `tests/tasks/check_header.yml`, and `.yamllint.yml` start with `# SPDX-License-Identifier: MIT`.
  Add that line as the first line of a new file when it is a sibling of those files.
  Do not add it to existing files that lack it only for this reason.

**`no_log` patterns:**

- Unlike most other Linux System Roles, this role does not define a `sshd_secure_logging` variable.
  The existing tasks that use `no_log` (`tasks/variables.yml`, `tasks/install_service.yml`) all use `no_log: "{{ ansible_verbosity < 3 }}"`.
  This hides the task output unless you run with `-vvv` or higher.
  Follow this existing pattern for tasks that only produce noisy or large output, such as facts:

  ```yaml
  - name: Ensure ansible_facts used by role
    ansible.builtin.setup:
      gather_subset:
        - min
        - virtual
    # This role has no sshd_secure_logging variable: hide the output unless -vvv
    no_log: "{{ ansible_verbosity < 3 }}"
  ```

- Currently the role handles no credentials or secrets in its tasks.
  If you add a task that does, do not rely on `ansible_verbosity` alone.
  Add a `sshd_secure_logging: true` variable to `defaults/main.yml`, `meta/argument_specs.yml`, and `README.md`, and use `no_log: "{{ sshd_secure_logging }}"`.
- NEVER use hardcoded `no_log: true` - always parametrize.

**Package installation (OSTree compatibility):**

- ALWAYS use the `ansible.builtin.package` module (NEVER `yum`, `dnf`, or `apt` directly).
- ALWAYS include the `use:` parameter for OSTree compatibility.
  It does nothing on non-OSTree systems.

  ```yaml
  - name: Ensure packages
    ansible.builtin.package:
      name: "{{ sshd_packages }}"
      state: present
      use: "{{ (__sshd_is_ostree | d(false)) | ternary('ansible.posix.rhel_rpm_ostree', omit) }}"
  ```

- `__sshd_is_ostree` is set in `tasks/variables.yml`.
  DO NOT set it again.
- See [README-ostree.md](README-ostree.md) for the rpm-ostree details.

**Using the `shell:` module:**

- ALWAYS use the `cmd` parameter to specify the script to run, never the free-form style.
- ALMOST ALWAYS use `executable: /bin/bash` unless you must use another shell.
  This role also runs on systems where `bash` may not exist (for example, Alpine, BSD, AIX), so keep scripts in tasks POSIX-compatible where you can.
- ALWAYS use `set -e`, `set -u`, and `set -o pipefail` (or combined as `set -euo pipefail`) as the first line of the script, where the shell supports `pipefail`.
- ALWAYS use `changed_when:`.
- If you need to detect whether the script changed something, have it exit with a specific code or print a value to stdout/stderr, `register:` the result, then use `changed_when:` and `failed_when:` conditionals.

**Third-party collections:**

- Neither `README.md` nor `contributing.md` bans non-`ansible.builtin` collections, and the role already uses two:
  `ansible.posix` (`rhel_rpm_ostree` package manager; `mount` in tests) and `fedora.linux_system_roles` (the `firewall` and `selinux` roles).
- Prefer `ansible.builtin` modules or the `command` module when they do the job cleanly.
  Use another collection when it is the better option.
- A collection must only be needed by an optional feature, and the role must keep working without it when that feature is not used.
  The collections are not installed automatically.
- When you add a collection, also:
  - Add it to `meta/collection-requirements.yml`, `tests/requirements.yml`, and `tests/requirements-no-fedora-lsr.yml` (if it is not an LSR collection).
  - Describe it in the "Optional requirements" section of `README.md`.
  - Check that every platform in the CI matrix `.github/workflows/ansible-check.yml` can install it.

**Referencing other system roles:**

- This role calls `fedora.linux_system_roles.firewall` and `fedora.linux_system_roles.selinux` with the FQCN (see `tasks/firewall.yml` and `tasks/selinux.yml`).
  Keep using the FQCN, and keep the `# noqa: var-naming[no-role-prefix]` comments where role variables are passed through `vars:`.
  Use a unique `loop_var` (such as `sshd_item`) to avoid conflicts with loops in the called role.

**Idempotency:**

- Tasks must be idempotent - safe to run multiple times without unintended changes.
- Use proper state parameters (`present`/`absent`, `started`/`stopped`, etc.).
- `command`/`shell` tasks should use `creates`/`removes` or `changed_when` to avoid false changes.
- Changing how a list option is rendered changes the generated `sshd_config` and makes the first run report `changed`.
  Call this out in the PR (see the NOTE in `README.md` about change #390).

**Check mode support:**

- All tasks should support check mode (`--check`).
- Use `check_mode: false` only when required (for example, fact gathering).
- Test that the role works with `--check --diff`.

**Test coverage requirement:**

- When you add new tasks, add matching coverage in `tests/`.
- New functionality MUST include test files (`tests/tests_*.yml`) that exercise the new code paths.
- Cover both success and failure or edge cases.

### Handlers - `handlers/main.yml`

- Handlers use `listen:` topics (for example, `sshd_daemon_reload`).
  Notify the topic, not the handler name.
- Keep the guards on the existing handlers (`sshd_allow_reload`, `sshd_allow_restart`, `__sshd_skip_virt_env`, `ansible_connection != 'chroot'`).
- A handler with sensitive data must hide it with `no_log`, using the rules above.

### Test playbooks - `tests/tests_*.yml`

**CRITICAL: Role invocation pattern:**

- NEVER use `ansible.builtin.include_role` directly.
- NEVER use `ansible.builtin.import_role` directly.
- NEVER use the `roles:` keyword.
- ALMOST ALWAYS use the wrapper in this repository:

  ```yaml
  - name: Run role
    ansible.builtin.include_tasks: tasks/run_role_with_clear_facts.yml
    vars:
      sshd_<parameter>: <value>
  ```

  The wrapper runs `meta: clear_facts` and then includes the role `ansible-sshd`.
  It supports the inputs `__sr_tasks_from`, `__sr_public`, and `__sr_failed_when`.
- The existing exceptions are:
  - `tests_invalid_input.yml` uses the `roles:` keyword to test that role arguments passed as keywords are accepted.
  - `tests_firewall_selinux.yml` uses `include_role` with `tasks_from: variables.yml` and `public: true` to read `__sshd_skip_virt_env`, and to call the `firewall` and `selinux` roles for setup and cleanup.
    It runs this role through the wrapper.
- The invalid input test file is named `tests_invalid_input.yml` (singular), not `tests_invalid_inputs.yml`.
  Update it when you add validation, because `meta/make_option_lists --check` requires it.

**Test quality requirements:**

- Tests run with `hosts: all`.
  CI runs every `tests/tests_*.yml` file on localhost in containers (see `.github/workflows/ansible-check.yml`), so tests change the real `/etc/ssh` of the test host.
- Back up and restore every file the test can change with the shared tasks.
  Declare the files in `__sshd_test_backup_files`, then include `tasks/backup.yml` at the start and `tasks/restore.yml` at the end.
  Many existing tests restore in a plain task at the end; for new tests, restore in an `always` section so a failure still cleans up:

  ```yaml
  - name: Test something
    hosts: all
    vars:
      __sshd_test_backup_files:
        - /etc/ssh/sshd_config
        - /etc/ssh/sshd_config.d/00-ansible_system_role.conf
    tasks:
      - name: Backup configuration files
        ansible.builtin.include_tasks: tasks/backup.yml

      - name: Test block
        block:
          - name: Run role
            ansible.builtin.include_tasks: tasks/run_role_with_clear_facts.yml
        always:
          - name: Restore configuration files
            ansible.builtin.include_tasks: tasks/restore.yml
            tags: tests::cleanup
  ```

- Tag cleanup tasks with `tests::cleanup` so you can skip cleanup while debugging.
- Do not leave a changed `sshd_config`, host keys, or a broken sshd service behind.
  A bad config can lock you out of a test machine.
- Use the `assert` module to verify the expected state after the role runs.
- To check that a generated file carries the managed header and the fingerprint, use `tasks/check_header.yml`.
- Cover both success and failure scenarios.
- Tests must be idempotent - a second run must not fail, and must not change anything.
- For new test files, add `# SPDX-License-Identifier: MIT` as the first line only if the tests nearby have it (see the SPDX note above).

### Templates - `templates/**/*.j2`

- Templates that write configuration files for sshd (`sshd_config*.j2`, `sysconfig.j2`, `auth_principals.j2`, `trusted-user-ca-keys.pub.j2`) start with these headers, in this order:

  1. `{{ ansible_managed | comment }}`
  2. `{{ "willshersystems:ansible-sshd" | comment(prefix="", postfix="") }}`

- For `sshd_config.j2` and `sshd_config_snippet.j2`, the headers come from `meta/01_ansible_head.j2`.
  Change them there, then regenerate.
- The systemd unit templates (`sshd.service.j2`, `sshd@.service.j2`, `sshd.socket.j2`) are user-replaceable and currently have no header.
  Do not add one unless you also update the tests that compare them.

### Variable definitions - `defaults/**/*.yml`

- All user-facing variables MUST be prefixed with `sshd_`.
- The sshd options themselves are the exception to naming style: `sshd_<OptionName>` uses the exact CamelCase name of the `sshd_config` keyword (for example, `sshd_PermitRootLogin`).
  Add `# noqa var-naming` where `ansible-lint` requires it.
- Also keep supporting the `sshd_config` dictionary (the keys are the same option names), the `sshd_match` and `sshd_match_1` ... `sshd_match_9` variables, and the deprecated `sshd` dictionary.
- All variables which have a definite default value must be declared in `defaults/main.yml`.
  Ansible does not load other files from `defaults/`.
- For every new variable, document it in `README.md` (description and usage example) and in `meta/argument_specs.yml`.
- If a variable should have **no default** (remain undefined unless the user sets it), do NOT add it to `defaults/main.yml`.
  Declare and document it only in `meta/argument_specs.yml`, without a `default:` key.
  A placeholder or empty default defeats the purpose of leaving it undefined.
  In role code, use `is defined` or `| default()` to guard against undefined variable access.
  Most `sshd_<OptionName>` variables are in this category, because the OS defaults and the user value are merged by the role.

### Variable definitions - `vars/**/*.yml`

- Internal variables MUST be prefixed with `__sshd_`.
- User-facing variables belong in `defaults/main.yml`, not here.
- Per-OS files are selected in `tasks/variables.yml` with `with_first_found`, in this order:
  `<distribution>_<version>.yml` (for Ubuntu, the LTS release), `<os_family>_<major version>.yml`, `<distribution>.yml`, `<os_family>.yml`.
  They typically set `__sshd_os_supported`, `__sshd_packages`, and `__sshd_defaults`; look at a similar existing file first.
- When you add support for a new platform or version:
  - Add the vars file.
  - Update `galaxy_info.platforms` in `meta/main.yml`.
  - Update the "Tested on" list in `README.md`.
  - Update the CI matrix in `.github/workflows/ansible-check.yml`, if the platform can be tested there.
  - For Red Hat family platforms, regenerate `.ostree/` files with `meta/make_ostree_packages_files`.
- Do not edit the generated `__sshd_option_vars` block in `vars/main.yml` (see above).

### Role argument validation - `meta/argument_specs.yml`

`argument_specs.yml` is the authoritative documentation and type or shape validation for every role variable.
Keep it in sync when you add, rename, or change a variable.

- **Document every user-facing variable** here: type, whether it is required, its default (if any), `choices`, and a clear `description`.
- Document nested suboptions (dicts or lists of dicts) the same way, recursively.
- Every `sshd_<OptionName>` for an option in `meta/options_body` MUST have an entry.
  `python3 meta/make_option_lists --check` enforces this in both directions.
- Variables that should stay undefined by default must NOT get a `default:` in `defaults/main.yml` (see above).
- `argument_specs.yml` validation is limited: it checks types and shapes, but it cannot express cross-field constraints, cannot fully validate polymorphic or `raw`-typed fields, and runs before the role gathers its own facts.
- When you need validation beyond that, add checks in `tasks/assert_role_vars.yml`.
  Use it when:
  - A value depends on another variable (cross-field validation).
  - A field accepts multiple shapes or types that `argument_specs.yml` cannot tell apart (for example, a string or a dict).
  - The check needs gathered facts or other runtime state.
  - Keep these checks minimal.
    Prefer `argument_specs.yml` for everything it can express.
- Add a test for every new check to `tests/tests_invalid_input.yml`.
- `argument_specs.yml` validation is only run on Ansible 2.11 and later; `tests_invalid_input.yml` guards those tests with `ansible_version.full is version("2.11", ">=")`.

### Python code - `library/*.py`, `meta/make_option_lists`

- Follow PEP 8.
- `library/sr_fingerprint.py` is an Ansible module that must stay compatible with old Python versions (it uses `from __future__ import ...` and `__metaclass__ = type`).
  Do not use f-strings or other Python 3-only syntax in it.
- `meta/make_option_lists` is a developer tool that runs on Python 3 only.

### Documentation - `README.md`

- Document all new user-facing variables, with a `####` heading per variable (or per group of related variables) in "Role variables", and include usage examples for new functionality.
- Markdown is checked by `markdownlint` with `.markdownlint.yaml` (line length is not limited), and spelling by `codespell`.
- Do not edit `.README.html` by hand.
- Keep the "Tested on" list in sync with `meta/main.yml` and the CI matrix.

### Checks to run before you submit

- `python3 meta/make_option_lists --check`
- `yamllint --strict .` (config: `.yamllint.yml`)
- `ansible-lint` (config: `.ansible-lint`)
- `markdownlint` and `codespell` for documentation changes
